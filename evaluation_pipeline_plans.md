# Evaluation Pipeline Architecture Plan

This document outlines the concrete, production-ready architecture for the cache evaluation pipeline, persistent audit storage, and feedback loops in Echo Gate.

---

## 1. Core Principles

1. **Zero Serving-Path Latency**: Evaluation runs completely out-of-band in asynchronous background tasks. The client receives the cached response immediately.
2. **Avoid the "Ratchet Trap"**: Telemetry cannot rely exclusively on cache misses/rejections (which induces selection bias and explodes error rates). We run a low-rate (1%–2%) random audit on approved cache hits to capture unbiased ground truth.
3. **Keep Vector Storage Stateless**: Avoid mutating statistical arrays and running logistic regressions inside Qdrant point payloads. PostgreSQL is the source of truth for evaluation history, and Qdrant remains an index for fast vector retrieval.

---

## 2. Pipeline Components

### A. Asynchronous Shadow Audit Trigger ([LlmRouterService](file:///Users/christopherpaul/projects/echo-gate/app/modules/llm/llm_router_service.py))
- When a request produces a semantic cache hit in Qdrant, roll a random sample probability ($p = 0.01$).
- If selected, immediately return the cached response to the client, and enqueue a background task (`self._background_tasks.add(asyncio.create_task(...))`):
  1. Request a fresh completion from the configured LLM provider for the user's prompt.
  2. Dispatch both the cached response and fresh response to `LlmJudgeService`.
  3. Persist the evaluation result into the `cache_evaluations` relational table.

### B. Lightweight Binary Judge (`LlmJudgeService`)
- Adopt the zero-shot equivalence evaluation prompt proven in vCache:
  ```text
  System: You are a judge evaluating whether two answers are semantically equivalent.
          Respond with only 'YES' if they convey the same meaning, or 'NO' if they differ significantly.
  Prompt: Answer 1: {cached_answer}

          Answer 2: {fresh_answer}

          Are these answers semantically equivalent?
  ```
- Evaluated via a fast, low-cost model (e.g. Gemini 1.5 Flash or GPT-4o-mini) to keep audit overhead minimal (~0.01%–0.05% of total LLM traffic cost).

### C. Persistent Storage (`cache_evaluations` Table)
A dedicated PostgreSQL table to record audit history:
- `id`: UUID (Primary Key)
- `request_id`: Request trace correlation ID
- `tenant_id`: Tenant / user scope
- `model_name`: Upstream LLM model requested
- `query_text`: User prompt
- `cached_answer`: Text served from cache
- `fresh_answer`: Fresh reference text generated by the provider
- `intent`: Intent classified by `IntentClassifierService`
- `vector_similarity`: Cosine similarity score from Qdrant
- `rerank_score`: Cross-encoder score from `RerankerService`
- `is_equivalent`: Boolean verdict from judge (`YES` -> `True`, `NO` -> `False`)
- `cache_point_id`: Qdrant point ID of the matched cache entry
- `redis_cache_key`: Redis exact cache key
- `latency_saved_ms`: Latency saved by the cache hit
- `created_at`: UTC timestamp

## 3. Feedback Mechanisms (Closing the Loop)

### A. Instant Eviction (The Kill Switch)
- If the LLM judge flags an audited cache hit as incorrect (`is_equivalent == False`):
  - The background task immediately executes a point deletion in Qdrant (`llm_cache_service.delete_point(cache_point_id)`) and deletes the key in Redis.
  - Poisoned, hallucinatory, or stale cache entries are purged instantly so no subsequent requests can hit them.

### B. Periodic Intent Threshold Calibration (Conformal Risk Control)
- Rather than real-time online threshold mutation (which causes feedback instability and jitter):
  - A scheduled batch job or admin CLI command analyzes the `cache_evaluations` table grouped by `intent`.
  - Computes the empirical threshold quantile needed to guarantee an error rate $\le \alpha$ (e.g., $\le 2\%$) for that intent.
  - Updates `config.CACHE_CONFIDENCE_THRESHOLDS` or overrides cached Redis keys (`cache:thresholds:{intent}`).

### C. In-Domain Fine-Tuning Dataset Export
- As evaluation records accumulate, export `(query_text, cached_answer, is_equivalent)` triples.
- Gray-zone pairs from real gateway traffic provide the exact dataset needed to fine-tune an in-domain cross-encoder reranker, turning noisy rerankers into domain-accurate verifiers.

## 4. Implementation Steps

1. **Database Model & Migration**:
   - Create `CacheEvaluationModel` in `app/modules/cache_evaluation/cache_evaluation_model.py`.
   - Generate and run Alembic migration: `poetry run alembic revision --autogenerate -m "create_cache_evaluations_table" && poetry run alembic upgrade head`.
2. **Build `LlmJudgeService`**:
   - Create `app/modules/llm/llm_judge_service.py` to execute the binary equivalence prompt via `LlmProviderService`.
3. **Wire Shadow Audit into `LlmRouterService`**:
   - Add random audit sampling ($p = 0.01$) to the semantic hit branch.
   - Enqueue async audit task to call judge and persist result in `cache_evaluations`.
4. **Implement Instant Eviction**:
   - On `is_equivalent == False`, trigger immediate deletion in Qdrant and Redis.
5. **Periodic Threshold Calibration Utility**:
   - Add a lightweight reporting and calibration utility to compute empirical risk per intent.
